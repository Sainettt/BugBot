# BugBot — платформа разбора багов и идей для нескольких проектов

Статус: черновик v2, 2026-09-22. Без привязки к конкретной реализации.
v1 (2026-09-22, утро) описывал сервис под один проект MAGGuarantee. v2 делает его многопроектным.

## 0. Что изменилось относительно v1

- **Проект — первоклассная сущность.** Подключение нового проекта = заполнить конфигурацию, а не лезть в код BugBot.
- **Доступ только для пользователей подключённого проекта.** В MAGGuarantee это сотрудники и внешние перевозчики. Никого больше. Проект сам говорит BugBot, кто пришёл, через короткоживущий handoff-токен.
- **Агент за интерфейсом провайдера.** Первый провайдер — Claude Code в headless-режиме (`claude -p`). Модель, лимиты и провайдер выбираются в конфигурации проекта.
- **Страница конфигурации** для владельца BugBot: подключение и настройка проектов через UI.
- Одна схема БД на все проекты с `project_id`, а не таблицы на каждый проект (почему — в разделе 8).

## 1. Что это и зачем

**BugBot** — «тревожная кнопка» для любого подключённого проекта.

- Пользователь проекта оставляет баг-репорт на alarm-странице этого проекта.
- Админ проекта (шеф) на скрытой странице оставляет идеи и хотелки.
- Каждое обращение уходит агенту, у которого есть клон репозитория проекта и знание о нём.
- Агент обновляет клон, разбирает обращение по коду и возвращает готовый контекст: где проблема, почему, что менять, риски, план.
- Отчёт приходит владельцу на почту (markdown + JSON).

Первый подключённый проект — MAGGuarantee. Следующие кандидаты — MAGSpace и всё, что появится потом.

Что **не** входит в первую версию: правки кода и PR от агента, диалог с агентом, публичный трекер статусов для репортеров.

## 2. Роли

| Роль | Кто это | Что делает | Где |
|---|---|---|---|
| Владелец BugBot | Ты | Подключает и настраивает проекты, получает отчёты, следит за очередью | `/admin` |
| Админ проекта | Шеф (и кто ещё назначен в конфиге проекта) | Оставляет идеи для своего проекта | `/p/<slug>/ideas` |
| Репортер | Пользователь подключённого проекта: сотрудник или внешний перевозчик | Оставляет баг-репорт | `/p/<slug>/alarm` |
| Агент | Claude Code (или другой провайдер) | Читает код, разбирает обращение, строит план | Agent runner |

Роли репортера и админа проекта определяются **на стороне проекта**, BugBot им доверяет через токен (раздел 5).

## 3. Проект как единица конфигурации

### 3.1 Что описывает конфигурация проекта

| Раздел | Что внутри | Пример для MAGGuarantee |
|---|---|---|
| **Основное** | slug, название, статус (активен / пауза), язык форм, язык отчёта | `magguarantee`, формы PL, отчёт RU |
| **Репозиторий** | URL, ветка по умолчанию, способ доступа (deploy key / токен), подпапка с кодом для монорепо, файлы, которые агент должен прочитать первыми | GitHub, `main`, `magguarantee-app/`, `CLAUDE.md`, `docs/` |
| **Агент** | провайдер, модель, effort, максимум ходов, таймаут, бюджет на запуск, профиль разрешённых инструментов | `claude-code`, модель Opus, 15 минут, только чтение |
| **Промпты** | «бриф» проекта (что это, где что лежит, глоссарий, чего не делать), переопределения базовых пресетов bug/idea | «оркестратор не вызывать, саб-агентов нет, только анализ» |
| **Доступ** | адаптер аутентификации и его параметры: ключ проверки токена, кто может репортить, кто видит страницу идей | handoff-токен от MAGGuarantee; репортить могут все роли; идеи — `admin` и email шефа |
| **Форма** | набор полей баг-репорта и идеи, справочники для выпадающих списков (роли, разделы приложения), лимиты вложений | список 8 ролей MAGGuarantee, разделы: заявки, авто, экспорт… |
| **Уведомления** | получатели по типу обращения, префикс темы письма, дополнительные каналы | bug → ты; idea → ты и шеф; `[MAGG]` |
| **Лимиты** | обращений на пользователя в день, размер вложений, параллельность разборов | 5 в день, 10 МБ, 1 разбор за раз |

### 3.2 Где хранится

- В Postgres, таблица `projects`: типизированные колонки для общего + JSONB для адаптер-специфичных настроек (параметры аутентификации, параметры провайдера).
- Секреты (deploy key, ключ проверки токена, ключи провайдеров) — отдельно: либо зашифрованы мастер-ключом из окружения, либо в БД хранится только имя переменной окружения, а значение живёт в env контейнера. Для старта второй вариант проще и безопаснее.
- Промпты и бриф — версионируются: каждое изменение создаёт новую версию, запуск агента запоминает, с какой версией работал.

### 3.3 Подключение нового проекта — что нужно сделать

На стороне BugBot (через страницу конфигурации, без кода):

1. Создать проект, заполнить основное.
2. Указать репозиторий, выдать read-only доступ, нажать «проверить»: runner клонирует и подтверждает.
3. Выбрать провайдера и модель, задать лимиты.
4. Написать бриф проекта (или взять из его `CLAUDE.md`).
5. Выбрать адаптер доступа, вставить ключ, скопировать контракт для интеграции.
6. Настроить получателей и поля форм.
7. Прогнать тестовый разбор на выдуманном баге.

На стороне подключаемого проекта (единственное место, где нужен код):

- Кнопка «Сообщить об ошибке» в интерфейсе проекта.
- Один эндпоинт, который для залогиненного пользователя выдаёт handoff-токен и перенаправляет в BugBot (раздел 5.3). Это несколько десятков строк.

Если проект без собственных пользователей (внутренняя утилита) — берётся адаптер «Google + allowlist» или «пароль по ссылке», и в проекте менять ничего не нужно.

## 4. Компоненты

```
 Проект A (MAGGuarantee)          Проект B (MAGSpace)
   кнопка "Сообщить" ──┐            кнопка "Сообщить" ──┐
                       │ handoff-токен                  │
                       ▼                                ▼
            ┌────────────────────────────────────────────────┐
            │  Web (Next.js)                                 │
            │  /p/<slug>/alarm   /p/<slug>/ideas   /admin    │
            └───────────────────────┬────────────────────────┘
                                    │
            ┌───────────────────────▼────────────────────────┐        ┌──────────┐
            │  API (NestJS)                                  │◄──────►│ Postgres │
            │  Projects · Auth(adapters) · Reports · Jobs    │        └──────────┘
            │  Agent(providers) · Notifications · Storage    │
            └───────────────────────┬────────────────────────┘
                                    │ задача (project, report, тип)
                                    ▼
            ┌────────────────────────────────────────────────┐
            │  Agent runner                                  │
            │  /workspaces/magguarantee   /workspaces/magspace│
            │  провайдер: claude -p | (позже другие)         │
            └───────────────────────┬────────────────────────┘
                                    │ отчёт (json) + лог + usage
                                    ▼
                          письмо получателям проекта
```

### 4.1 Web (Next.js)

- `/p/<slug>/alarm` — форма баг-репорта проекта. Поля и язык из конфигурации. Доступна только с сессией BugBot, полученной через handoff.
- `/p/<slug>/ideas` — форма идеи. Доступна только тем, кого конфигурация проекта отнесла к админам.
- `/p/<slug>/auth/callback` — приём handoff-токена, создание сессии, редирект на нужную форму.
- `/admin` — кабинет владельца: лента обращений и идей по всем проектам с готовыми отчётами, конфигурация проектов, очередь, перезапуски (раздел 9). Вход через Google, разрешённые email заданы в окружении.
- Формы мультиязычные: перевозчики MAGGuarantee работают на польском, значит форма MAGGuarantee — PL по умолчанию.

### 4.2 API (NestJS)

- **Projects** — CRUD проектов и их конфигурации, версии промптов, проверка репозитория, тестовый запуск.
- **Auth** — набор адаптеров аутентификации (раздел 5). Общий результат адаптера: «это пользователь X проекта Y с ролями Z» или отказ. Сессии BugBot.
- **Reports** — приём обращений в контексте проекта, валидация по схеме формы проекта, лимиты, статусы.
- **Jobs / Queue** — очередь разборов, воркер, ретраи, таймауты, блокировка «один разбор на проект».
- **Agent** — сборка промпта из слоёв (раздел 6.4), выбор провайдера по конфигу, вызов runner, валидация результата по схеме.
- **Notifications** — письма получателям проекта, генерация markdown из JSON.
- **Storage** — вложения, разложенные по проектам.

### 4.3 Очередь и воркер

- Обращения обрабатываются асинхронно, API отвечает сразу.
- Очередь — таблица `jobs` в Postgres на старте (BullMQ + Redis, когда понадобятся приоритеты и дашборд).
- Блокировка на уровне проекта: одновременно один разбор на проект (клон один, `git checkout` двух веток сразу не сделать). Глобальный лимит параллельности — из настроек BugBot.

### 4.4 Agent runner

- Один контейнер с git и установленными провайдерами. Внутри — по рабочей папке на проект: `/workspaces/<slug>`, постоянный volume.
- Перед разбором: `git fetch`, `git checkout <ветка>`, `git pull`. Коммит записывается в запуск.
- Принимает задачу: рабочая папка, провайдер, модель, лимиты, собранные промпты, вложения. Возвращает: JSON-результат, сырой лог, usage, стоимость, причину завершения.
- Если какому-то проекту понадобится своё окружение или строгая изоляция — режим «выделенный runner» для проекта: тот же образ, отдельный контейнер, свой volume. Переключается в конфиге, интерфейс не меняется.

### 4.5 Postgres

Одна схема, все таблицы с `project_id`. Модель — в разделе 8.

### 4.6 Почта

Транзакционная отправка. Получатели и префикс темы — из конфигурации проекта. Письмо: резюме в теле, ссылка на карточку обращения в кабинете, `report.md` и `report.json` во вложении. Письмо — уведомление, источник правды — кабинет.

## 5. Доступ: кто может репортить

### 5.1 Требование

В MAGGuarantee репортить будут и сотрудники MAGTRANS, и внешние перевозчики (`przewoznik`). Пускать можно только тех, кто есть в MAGGuarantee. BugBot не должен вести свой список пользователей и не должен знать пароли проекта. Значит, **источник правды о том, кто пришёл, — сам проект.**

### 5.2 Варианты

| Вариант | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **A. Handoff-токен от проекта** | Пользователь нажимает кнопку в проекте → проект выдаёт короткоживущий подписанный токен с id/email/ролями → редирект в BugBot → BugBot проверяет подпись и открывает сессию | Проект остаётся источником правды, ни одного лишнего пароля, работает для любого проекта с логином, перевозчики проходят так же, как сотрудники | В каждом проекте нужен один эндпоинт и кнопка |
| B. Проверять существующий JWT проекта | BugBot знает секрет/ключ проекта и принимает его access-токен | Ничего не менять в проекте | Токен MAGGuarantee живёт в HttpOnly-cookie на домене проекта, BugBot на другом домене его не увидит; общий секрет подписи — плохая практика |
| C. Форма внутри проекта | Проект сам рисует форму и шлёт обращение в BugBot server-to-server | В BugBot вообще нет аутентификации пользователей | Форму и её эволюцию придётся повторять в каждом проекте; BugBot вырождается в API |
| D. Синхронизация списка пользователей + magic link | BugBot периодически тянет пользователей проекта, вход по ссылке на email | Не зависит от сессии проекта | Ещё одна копия пользователей, задержка синхронизации, лишний шаг для перевозчика |
| E. Google + allowlist | Вход через Google, список разрешённых email в конфиге | Просто | Перевозчики не в Google Workspace MAGTRANS, для них не работает |

### 5.3 Рекомендация: handoff-токен (A)

```
 Пользователь в MAGGuarantee (уже залогинен)
        │ нажимает "Сообщить об ошибке"
        ▼
 MAGGuarantee API: GET /integrations/bugbot/handoff?kind=bug
        │ проверяет сессию, собирает claims, подписывает токен (60 секунд, одноразовый)
        │ 302 → https://bugbot/p/magguarantee/auth/callback?token=...
        ▼
 BugBot: проверяет подпись ключом из конфига проекта, срок, аудиторию, jti
        │ создаёт сессию BugBot (cookie, несколько часов, привязана к проекту)
        ▼
 /p/magguarantee/alarm — форма, уже знающая кто пришёл и в какой роли
```

Контракт токена (общий для всех проектов):

- `iss` — slug проекта, `aud` — `bugbot`, `exp` — минута, `jti` — одноразовый.
- `sub` — id пользователя в проекте, `email`, `name`, `roles[]`, опционально `locale` и `extra` (для MAGGuarantee — `carrierId`).
- Подпись асимметричная (ES256/RS256): проект хранит приватный ключ, BugBot — публичный. Утечка конфига BugBot не даёт подделать токен.

Как это ложится на MAGGuarantee: у него уже есть JWT с `sub`, `role`, `carrierId` и практика межсервисных токенов с MAGSpace. Эндпоинт handoff — это `@Roles(все)` + подпись. Перевозчик проходит через свой обычный вход (логин + 2FA), сотрудник — через Google SSO, для BugBot разницы нет.

Активность пользователя проверяется в момент выдачи токена: уволенный сотрудник или отключённый перевозчик в проект уже не войдёт, значит и токен не получит. Сессия BugBot короткая, повторный handoff — один клик.

### 5.4 Кто видит страницу идей

В конфигурации проекта два правила, применяются к claims из токена:

- `reporters`: какие роли могут репортить (для MAGGuarantee — все).
- `admins`: какие роли и/или какие конкретные `sub`/email видят страницу идей (для MAGGuarantee — роль `admin` плюс email шефа, если у него другая роль).

Страница идей не «скрытая по URL», а закрытая по правилу. Знание адреса ничего не даёт.

### 5.5 Адаптеры для других проектов

Адаптер — сменная стратегия, проект выбирает одну:

- `handoff-jwt` — основной, для любого проекта с собственным логином (MAGGuarantee, MAGSpace).
- `google-allowlist` — для внутренних утилит без своих пользователей: вход через Google, список email в конфиге.
- `shared-password` — для приватных или тестовых проектов: одна ссылка с паролем. В прод не рекомендуется.

Все адаптеры возвращают одинаковый объект «пользователь проекта», дальше BugBot работает одинаково.

### 5.6 Сессии и защита от злоупотреблений

- Сессия BugBot привязана к проекту: сессия из MAGGuarantee не открывает формы MAGSpace.
- Лимит обращений на пользователя в сутки из конфига. Аутентификация не отменяет лимиты: перевозчик тоже может нажать кнопку двадцать раз.
- В обращении сохраняется, кто его оставил (`sub`, email, роль) — это уходит и в отчёт агенту, потому что роль репортера в MAGGuarantee важна для локализации бага.

## 6. Агент: провайдеры и модели

### 6.1 Интерфейс провайдера

Абстрактно: провайдер принимает задачу и возвращает результат.

- Вход: рабочая папка, системный промпт, промпт задачи, вложения, модель, лимиты (ходы, время, бюджет), профиль инструментов.
- Выход: текст/JSON результата, сырой лог, usage (токены), стоимость, причина остановки (готово / лимит / таймаут / ошибка).
- Провайдер объявляет: список поддерживаемых моделей, умеет ли принимать изображения, умеет ли структурированный вывод.

Остальная система провайдер-агностична: очередь, промпты, валидация, письма одинаковы для всех.

### 6.2 Провайдер `claude-code` (первый)

- Запуск `claude -p` в рабочей папке проекта. Параметры конфига ложатся на флаги CLI: модель, JSON-вывод, дополнительный системный промпт, разрешённые инструменты, максимум ходов. Таймаут и бюджет контролирует runner снаружи.
- JSON-вывод CLI уже содержит usage и стоимость — это пишется в запуск.
- Выбор модели — из списка провайдера в конфиге проекта. Можно задать разные модели для bug и idea (например, идеи разбирать сильной моделью, простые баги — дешевле).
- Аутентификация провайдера — API-ключ в окружении runner. Один ключ на BugBot, расход раскладывается по проектам по usage из запусков.

### 6.3 Другие провайдеры (потом)

- Другие агентные CLI с headless-режимом (аналоги Claude Code от других вендоров) — тот же контракт: cwd, промпт, JSON на выходе.
- Claude Agent SDK — та же начинка Claude Code как библиотека, если захочется убрать child-process и получить хуки на каждый шаг.
- «Прямой API + свой цикл инструментов» — для моделей, у которых нет агентного CLI. Дороже в поддержке, оставить на случай реальной потребности.

Что важно спроектировать сейчас: контракт провайдера и хранение «провайдер + модель» в конфиге. Сами провайдеры добавляются по одному.

### 6.4 Сборка промпта: слои

1. **Базовый пресет** по типу (bug / idea) — общий для всех проектов, лежит в репозитории BugBot, версионируется.
2. **Бриф проекта** из конфига — что это за система, где что лежит, глоссарий, чего не делать. Для MAGGuarantee сюда идёт: «есть `CLAUDE.md` и `docs/`, читай их; оркестратора и саб-агентов не вызывать; легаси `Code.gs` — только референс».
3. **Переопределения проекта** для пресета, если базовый не подходит.
4. **Схема результата** — JSON-схема ответа, единая для типа обращения.
5. **Данные обращения** — в явно размеченном блоке как недоверенные данные: поля формы, роль репортера, вложения.

Проект-специфичный `CLAUDE.md` в репозитории подхватывается автоматически: это плюс, но и причина, по которой нужен слой 2 — чтобы отменить то, что в нём написано для разработки, а не для анализа.

### 6.5 Гарантия структуры результата

- Ответ валидируется по JSON-схеме на бэке, независимо от провайдера.
- Если не прошёл — одна попытка «починить»: агенту отправляется его ответ и ошибки схемы. Если снова нет — запуск `failed` с сырым логом.
- Markdown для письма генерирует бэк из валидного JSON.

## 7. Основной сценарий

1. Пользователь в проекте нажимает «Сообщить об ошибке» → handoff → сессия BugBot → форма проекта.
2. Заполняет форму → API проверяет сессию, правило доступа, лимиты, схему формы проекта → обращение `queued` с `project_id` и данными репортера.
3. Воркер берёт задачу, проверяет блокировку проекта, переводит в `running`.
4. Модуль Agent собирает промпт по слоям, берёт провайдер и модель из конфига проекта.
5. Runner: обновляет рабочую папку проекта → запускает провайдера → отдаёт результат, лог, usage.
6. Бэк валидирует результат, сохраняет запуск, статус `done`.
7. Письмо получателям проекта: тема `[<префикс>][bug] #N: заголовок`, резюме, вложения.
8. При ошибке: ретраи по политике, потом `failed` и письмо с логом владельцу.

Разборы разных проектов идут параллельно в пределах глобального лимита, внутри одного проекта — по очереди.

## 8. Модель данных

- **Project** — конфигурация из раздела 3.1: типизированные поля + JSONB для адаптер- и провайдер-специфичного.
- **PromptVersion** — версии брифа и переопределений проекта; базовые пресеты версионируются в git BugBot.
- **Session** — сессия BugBot: проект (пусто для сессии владельца), `sub`, email, имя, роли, срок.
- **Report** — обращение: проект, тип, поля формы (JSON), репортер (`sub`, email, роль), статус разбора, ветка/коммит для анализа, статус обработки владельцем (new / seen / handled / archived), заметка владельца.
- **Attachment** — вложение: проект, обращение, файл в хранилище.
- **AgentRun** — запуск: обращение, провайдер, модель, версия промптов, коммит, время, токены, стоимость, `result_json`, `result_md`, ошибка, лог.
- **Notification** — отправленные письма.
- **UsedHandoffToken** — `jti` использованных токенов на время их жизни, чтобы токен нельзя было переиграть.

**Почему одна схема, а не таблицы на проект.** Отдельные таблицы означают: миграции умножаются на число проектов, код обрастает выбором таблицы по имени, общая очередь и статистика по всем проектам становятся мучением, а подключение нового проекта требует DDL. С `project_id` подключение — это строка в `projects`. Изоляция данных обеспечивается внешними ключами и проверкой проекта в каждом запросе; если когда-нибудь понадобится жёстче — row-level security в Postgres, без изменения схемы. Единственный аргумент за отдельные таблицы — разная структура обращений у разных проектов, но она уже покрыта JSON-полем формы со схемой из конфига.

## 9. Кабинет владельца (`/admin`)

Только для владельца BugBot. Письма остаются уведомлением, кабинет — место, где живёт вся информация. Из письма ведёт ссылка на карточку обращения.

### 9.1 Вход

- Google-вход. Список разрешённых email — в переменной окружения BugBot (например `ADMIN_EMAILS`, через запятую, чтобы второго человека можно было добавить без кода).
- Бэк проверяет подпись id_token, флаг подтверждённого email и вхождение адреса в список. Сессия — HttpOnly-cookie, отдельная от сессий проектов.
- С адаптерами проектов не связан: это вход только в кабинет.
- Запасного парольного входа нет. Если Google недоступен, письма всё равно приходят. Break-glass пароль в env можно добавить позже, если понадобится.
- OAuth-клиент Google можно завести отдельный для домена BugBot или переиспользовать существующий у MAGGuarantee / MAGSpace, добавив redirect URI.

### 9.2 Обращения — главный экран

- **Лента по всем проектам**: проект, тип (bug / idea), заголовок, репортер и его роль, статус разбора, время, стоимость. Фильтры по проекту, типу, статусу, дате. Непросмотренные подсвечены.
- **Сводка сверху**: в очереди, в работе, упавшие, расход за месяц по проектам.
- **Карточка обращения**: исходные поля и вложения, отчёт агента в читаемом виде (markdown из JSON), метаданные запуска (провайдер, модель, версия промпта, коммит, время, токены, стоимость), сырой лог, история перезапусков.
- **Действия**: перезапустить (можно сменить модель или версию промпта и сравнить отчёты рядом), пометить как просмотрено / в работе / закрыто, заметка для себя, скачать `report.md` и `report.json`. Позже — «создать issue».
- Статус разбора (queued / running / done / failed) и твой статус обработки (new / seen / handled / archived) — разные поля.

### 9.3 Конфигурация проектов

**Список проектов.** Статус, число обращений в очереди, последний разбор, расход за месяц.

**Карточка проекта — вкладки по разделам конфига:**

- *Основное* — slug, название, языки, статус.
- *Репозиторий* — URL, ветка, подпапка, ключ. Кнопка «Проверить»: runner делает clone/fetch и показывает последний коммит.
- *Агент* — провайдер (выпадающий список), модель (список от провайдера), effort, лимиты, профиль инструментов. Кнопка «Тестовый разбор» на выдуманном обращении: показывает результат, время, стоимость.
- *Промпты* — бриф, переопределения, предпросмотр собранного системного промпта, история версий с откатом.
- *Доступ* — адаптер, ключ, правила `reporters` / `admins`. Рядом — готовый текст контракта для разработчика проекта: адрес callback, формат токена, пример.
- *Формы* — конструктор полей (тип, обязательность, подписи на языках), справочники для списков.
- *Уведомления* — получатели по типу, префикс темы, тест письма.

### 9.4 Настройки BugBot

Глобальная параллельность, ключи провайдеров (только имена переменных окружения), адрес отправителя.

Конфигурация экспортируется в файл и импортируется обратно — удобно для переноса между стендами и для хранения в git.

## 10. Безопасность

- **Токены handoff**: асимметричная подпись, минута жизни, одноразовый `jti`, обязательные `aud` и `iss`. Публичный ключ в конфиге проекта.
- **Сессии BugBot**: HttpOnly-cookie, привязка к проекту, короткий срок.
- **Изоляция проектов**: каждый запрос к данным фильтруется по проекту из сессии; рабочие папки runner разделены; вложения разложены по проектам.
- **Runner**: только чтение, read-only ключи к репозиториям, сеть ограничена git-хостингами и API провайдеров. Секреты продакшена подключённых проектов в runner не попадают никогда.
- **Prompt injection**: данные обращения — недоверенный блок; агент лишён инструментов записи, ущерб ограничен качеством отчёта.
- **Секреты BugBot** — в окружении контейнеров, в БД только ссылки по имени.
- **Отчёты** содержат фрагменты кода — только получателям из конфига, страница `/admin` только владельцу.
- **Кабинет `/admin`** — отдельная аутентификация владельца через Google, список email в окружении, не через проекты. Кабинет показывает код и отчёты всех проектов, поэтому список должен оставаться коротким.

## 11. Инфраструктура

- Монорепо BugBot: `apps/web`, `apps/api` (API + воркер), `apps/agent-runner`, `packages/shared` (схемы результата, схемы конфига, контракт провайдера и адаптера, типы).
- `docker-compose`: web, api, worker, postgres, agent-runner, mailpit для локальной почты; redis и выделенные runner'ы — по необходимости.
- Volume `/workspaces` у runner — клоны всех проектов переживают перезапуск.
- Хостинг — тем же способом, что MAGGuarantee и MAGSpace (VPS, compose, TLS-прокси), отдельным стеком.

## 12. Этапы

**Этап 0 — каркас.** Монорепо, Next + Nest + Postgres, compose, миграции с `Project` с самого начала, `packages/shared` со схемами результата, конфига, контрактами провайдера и адаптера.

**Этап 1 — проект и приём.** Сущность Project, минимальная страница конфигурации (основное, репозиторий, доступ), адаптер `handoff-jwt`, формы alarm и ideas в контексте проекта, хранение обращений. Параллельно — кнопка и эндпоинт handoff в MAGGuarantee. Результат: перевозчик или сотрудник MAGGuarantee может оставить обращение, чужой — нет.

**Этап 2 — агент вручную.** Runner с рабочими папками, провайдер `claude-code`, слои промптов, бриф MAGGuarantee, схема результата, тестовый разбор из `/admin`. Замер времени и стоимости, подбор модели и лимитов. Результат: из обращения получается полезный отчёт.

**Этап 3 — полный цикл.** Очередь, воркер, блокировка по проекту, автоматический запуск, письма получателям. Результат: обращение из формы → письмо без участия человека.

**Этап 4 — конфигурация и надёжность.** Остальные вкладки `/admin` (промпты с версиями, формы, уведомления), ретраи, бюджеты, перезапуск с другой моделью, экспорт/импорт конфига. Подключение второго проекта (MAGSpace) как проверка, что код не трогали.

**Этап 5 — расширения.** Второй провайдер, Telegram/Slack, автосоздание issue, черновик PR, ответ репортеру, дедупликация.
